# Scope

> A family-tree wiki, written by AI agents.

A one-page statement of what whoami.wiki is, who it is for, and — most
importantly — what it is *not*. When a feature is proposed, this is
the document that makes "no" easy.

---

## What this is

whoami.wiki is a **private, local-first encyclopedia of a family tree**,
generated by AI agents from a single GEDCOM source plus the user's
research notes. Two halves, joined:

1. **Tree.** `/family/tree` — interactive browser of ancestors,
   descendants, siblings, cousins, lifespans, and birthplaces, derived
   from a GEDCOM file plus per-individual derived YAML records.
2. **Articles.** Wiki pages at `/[slug]` about the people, places, and
   events on the tree. Written by an AI agent (Claude Code, Codex,
   OpenCode) reading the GEDCOM-derived data and the user's research
   notes; the agent cites its sources and surfaces open questions on
   the talk page.

The two halves share a data model: a person's article infobox and their
node on the tree render from the same `DerivedRecord`. Editing one is
editing the other.

**Product hypothesis:** LLMs already know the wiki form deeply
(Wikipedia is in their training data). The wiki form is therefore a
natural medium for organizing genealogy that an agent can produce well
and a human can browse intuitively.

---

## Target user

The product is sized for **one person**: the user, browsing on their
own machines (local plus Tailscale). Trusted family members may be
invited as guests — browsing over Tailscale, or through the
invite-only Descope gate on the Render replica. The wiki is not
designed to be public.

Constraints that follow:

- **Auth is env-gated.** Locally there is no login wall — Tailscale
  ACLs are the access layer, as before. The Render replica sets
  `WHOAMI_AUTH=on`, enabling the invite-only Descope gate (see the
  render deployment spec).
- **Local-first.** The data repo (`$WHOAMI_ROOT`, default `~/whoami`)
  is the source of truth. The code repo holds tooling.
- **Privacy by trusted access.** Living-person data flows through the
  system without redaction because every viewer is trusted — locally
  via Tailscale ACLs, and on the Render replica via the invite-only
  Descope gate. The replica leaves the user's network but not the
  circle of invited family. (ROADMAP P0.2's content-level redaction
  gate stays parked unless a less-trusted "guest" tier is introduced.)

## In scope

- GEDCOM ingestion and per-individual derivation
- Family graph: ancestors, descendants, siblings, cousins, cohort,
  relationship labels, lifespans, places-of-birth
- Article authoring by AI agents via the `wai` CLI (`read`, `write`,
  `create`, `edit`, `delete`, `search`, `sync-gedcom`, `recite`,
  `note`, `rebuild-search`, `migrate`, `healthz`, `config`)
- Talk pages as the agent's working memory (active gaps, decisions,
  agent log, structured research notes with edit/soft-delete)
- **Browser-side contribution to research notes and talk pages**
  (text, audio file refs, structured Q&A) via the `/api/notes` route
  family. Attribution is stored as a content field (`contributor:`,
  `recorded_by:`), not as a logged-in user identity — the Tailscale +
  single-user-device model holds. Decision: 2026-05-19. The contribution
  surface exists to let family informants (grandparents, parents) add
  context during in-person sessions without dropping to the CLI.
- Search across articles and GEDCOM-derived metadata
- Eval suite for benchmarking agent harness × model on article quality
- **Public deployment (added 2026-05-20).** The wiki may be deployed
  to a public host (Render) as a read-write replica, gated by the
  invite-only Descope auth flow. This reverses the former "no public
  hosting" and "no app-layer auth" anti-goals. The Mac Studio remains
  the canonical copy and the local-first model is preserved — see the
  render deployment spec (`docs/superpowers/specs/2026-05-20-render-deployment-design.md`).

## Out of scope (anti-goals)

These are *durable* exclusions, not "not yet" items. Reopen them only
with an explicit re-evaluation of the privacy posture or the
single-user model.

- **Multi-user concurrent editing.** No real-time collaboration,
  no merge-conflict UI. Per-user editor names are attribution only.
- **Tree editing in the browser.** GEDCOM and derived YAMLs are
  authored externally (RootsMagic, Gramps, Ancestry) or via the `wai`
  CLI. The browser does not write to `.ged` or `genealogy/derived/*.yml`.
  *Note: browser writes to research notes and talk pages are explicitly
  in scope — see the In scope section.*
- **Generic CMS features.** No themes, no plugin system, no media
  library beyond what genealogy needs (portraits, scans, documents).
- **Apple-style sparseness.** Information density wins. The audience
  is researchers scanning and comparing data, not magazine readers.
- **Page-chrome flourishes.** No parchment / sepia / gradient page
  tints, no drop caps, no noise overlays. Creativity in type and
  layout is welcome; tinting page chrome is not.
- **Mobile-first.** Mobile must work; mobile is not the design center.
  Genealogy research happens at a desk.

## Architectural constraints

These are gates on *how* features ship, regardless of what they do.

- **`core/` is platform-agnostic.** Pure TypeScript, no React, no I/O
  above the function boundary. Tests pass `Map<string, DerivedRecord>`
  rather than reading files.
- **`frontend/` is Next 16 App Router.** RSC by default. Auth is
  `WHOAMI_AUTH`-gated (off locally, on for the Render replica). Read
  `frontend/AGENTS.md` and `node_modules/next/dist/docs/` before
  writing Next code from training-data instinct.
- **Tests run via `tsx --test`.** Not Jest, Vitest, or Bun. Tests use
  `node:test` and `node:assert/strict`, live next to the module.
- **TypeScript everywhere; `tsc --noEmit` is the gate.**
- **Conventional commits.** `type: subject` — lowercase, no scope,
  imperative mood, ≤72 chars, no trailing period.

## The stranger test

Whether a file belongs in this code repo or in `$WHOAMI_ROOT` is a
**privacy** question, not a content question. The rule:

> Could I show this file to a stranger without revealing anything
> about the user?

If the **list of entries** would tell a stranger about the user's
life — even if every individual value is impersonal — it is user
data and lives in `$WHOAMI_ROOT`.

Canonical example: `genealogy/places-coords.yml`. Every coordinate is
universal geography (Kyiv is at 50.45, 30.52 regardless of whose family
is from there), but the *list* of which places appear is "places this
user's ancestors lived." User data.

When in doubt, lean toward user data. The cost of two-repo coordination
is the price of an honest privacy boundary.

---

## When in doubt about a feature

A four-question check, in order:

1. **Does it serve the single-user, local-first reading and research
   loop?** If no, stop.
2. **Does it introduce auth, multi-user state, or public sharing?**
   If yes, stop and re-open the scope conversation; do not slip it in.
3. **Does it move logic outside `core/` boundaries?** If yes,
   refactor to keep `core/` pure.
4. **Does it add page-chrome decoration?** If yes, redirect to type
   or layout choices instead.
